# Set up ongoing feedback

When the user asks to get started or set up this skill, guide them through connecting their work sources and creating the recurring review. Explain that the intended cadence is every 30 minutes, with useful feedback delivered privately. For a one-off draft or conversation review, go straight to the review; don't require onboarding or create a schedule.

1. **Discover and connect sources.** Check the host's available connections first. Encourage the user to connect Slack or Microsoft Teams, whichever they use, and the tool they use to record or take notes in meetings. Meeting material may be available through the recorder's own connector or an authorized transcript/notes folder. Ask what they use if it isn't apparent. Guide them through the host's normal connection flow; never ask them to paste credentials. Don't claim support for a service without checking the available tools. Connecting a recorder does not authorize starting new recordings.
2. **Resolve scope and identity.** Identify the user's account in each service. Establish which workspaces, teams, channels/conversations, and meeting sources they want reviewed, their personal timezone, any preferred operating hours, and the private destination for feedback. Reuse details and authorization already supplied. Ask only for missing choices. Exclude other people's DMs or private sources unless the user has authorized that scope and the host permits access. Ask for one useful personal goal, such as showing reasoning or asking about constraints, without making calibration a prerequisite.
3. **Verify access before scheduling.** Read a small authorized sample of a relevant thread and available meeting material. Check that the future scheduled task can use these connections and reach the private destination. If a connection needs login, reconnection, or approval, finish that step before including it. If a source isn't supported or meeting attribution is unavailable, explain the gap and offer a supported source or a narrower review. Don't silently promise coverage or create a task assuming access will work later.
4. **Create the automation.** Use the host's supported scheduling tool to create a recurring Executive Feedback task once source scope, destination, and cadence are authorized. A clear setup request with those choices already supplied is sufficient; don't ask for the same permission again. First check for an existing matching task and update it instead of creating a duplicate. Prefer an exact 30-minute cadence if the host permits it. If the host has a longer minimum interval, explain the limitation and offer its nearest supported cadence; get the user's acceptance before saving the changed cadence. For example, if the host supports hourly runs at most, offer hourly. Never approximate 30 minutes with staggered tasks or another workaround that bypasses a platform limit. If no scheduler is available, explain what remains manual rather than claiming setup succeeded.
5. **Verify and hand off.** Inspect the saved task's actual schedule, sources, and destination. Tell the user what was connected, the actual cadence and operating hours/timezone, known coverage gaps, and how to pause or change the task. Distinguish checks from notifications: review on schedule, but send feedback only when it is useful and new. Do not promise immediate coverage; meeting material can arrive after the meeting ends.

## Scheduled task instructions

Make the task self-contained: include the resolved user identity, authorized sources/scope, private destination, initial review start time, and personal calibration. Include the coaching criteria and boundaries in [SKILL.md](../SKILL.md) in the task prompt, or provide a durable copy of this skill that the scheduled execution can actually read. Don't rely on memory of the setup chat.

In each run:

- Review the user's new or changed work messages and newly available or updated meeting notes/transcripts in the authorized scope. Read relevant prior context and latest replies before giving feedback. For meetings, verify attribution and distinguish summaries from speech. Availability of a transcript, not just the meeting's start time, determines whether it is new to the review.
- Track a last-successful checkpoint for each source and use a small overlapping retrieval window. Track stable message or meeting identifiers plus the issue already covered to avoid repeating feedback. Review changes that materially alter the assessment, including repairs. Record attribution-uncertain meeting material as inspected but unassessable for that version, suppress repeat notices, and reconsider it when the document or attribution changes. For sources without reliable updated/availability filters, use a bounded recheck of recent meetings and deduplicate by document ID/version; disclose any remaining late-arrival gap.
- Start at the agreed activation time unless the user requested a historical review. Persist checkpoints and feedback history privately using the host's supported task state or private storage, never in this repository or a shared work channel. Advance a source checkpoint only after its retrieval and review succeed. Preserve retryable feedback if delivery fails. If reliable state or private delivery isn't available, explain the limitation before enabling unattended reviews.
- Coach curiosity before rebuttal, visible reasoning and trade-offs, clear exploration/request/decision intent, and ownership of the next step. Reinforce good behavior when it teaches something. Send only useful, new feedback to the designated private destination, with a source reference, explanation, and a short suggested alternative where helpful. Stay silent when there is nothing useful to add; don't send routine scores or empty check-in reports.
- If a source fails, don't treat that as a clean review. Continue independent available sources, retain the failed source's checkpoint, and privately surface actionable access failures without repeatedly notifying about the same outage. Don't expand source scope, restart recordings, change schedules, or contact coworkers.
